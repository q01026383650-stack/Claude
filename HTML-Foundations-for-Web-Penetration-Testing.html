Preface

Why HTML Before Pentesting?

Many beginners rush into learning attack tools without understanding the target. This book closes that gap.

Web penetration testing is the practice of finding security weaknesses in web applications. Every web application — from a simple blog to a banking portal — is built on the same three foundational technologies: HTML, CSS, and JavaScript. Of these three, HTML is the bedrock. It defines the structure, the content, the forms, the links, and the layout of everything the browser displays.

A penetration tester who doesn't understand HTML is like a locksmith who doesn't know how locks work. You might be able to follow a tutorial, but you'll be lost the moment something behaves unexpectedly — and in real-world testing, unexpected behaviour is the rule, not the exception.

What You Will Learn

  • How HTML documents are structured and parsed by browsers
  • Every major HTML element and what it does
  • How attributes, events, and values work
  • How forms collect and send data to servers
  • How links, URLs, and navigation work
  • What the DOM is and why it matters
  • How HTML, CSS, and JavaScript work together
  • How to read and analyse any web page's HTML source
  • How to use browser Developer Tools like a pentester
  • How HTML connects to HTTP headers and server communication
📌
This is NOT a hacking book

This book contains zero attack payloads. It is a pure foundations book. The skills you build here are the prerequisites that make the actual security topics — XSS, CSRF, injection, clickjacking — make sense when you study them next.

How to Use This Book

Read each chapter in order. After each section, open a browser and a text editor, and try the examples yourself. The best way to understand HTML is to write it, break it, and observe what happens. Use browser DevTools (F12) throughout — it is your window into how the browser interprets your code.

🛠️
Setup: What You Need

A text editor (VS Code is recommended), any modern browser (Firefox or Chrome), and that browser's DevTools (press F12). No server, no database, no special software is needed for 90% of this book. Just save a .html file and open it.

Chapter 01

What is HTML?

HTML — HyperText Markup Language — is the language browsers use to understand and display web pages. It is not a programming language; it is a markup (description) language.

1.1 A Brief History

HTML was invented by Tim Berners-Lee in 1991 as a way to share scientific documents over the internet. The "HyperText" part refers to links — text that connects documents together. The "Markup" part means it uses tags to annotate text with meaning. The earliest version had no version number and could not even display images — the <img> element only arrived in 1993 with the Mosaic browser.

Version Year Key Addition
HTML (first tags) 1991 Plain text and hyperlinks (no images yet)
HTML 2.0 1995 First formal standard (RFC 1866); forms introduced
HTML 3.2 1997 Tables, applets, text flow around images
HTML 4.01 1999 Scripting, stylesheet (CSS) linking, frames, accessibility
XHTML 1.0 2000 Stricter XML-based syntax
HTML5 2014 / living standard Audio, video, canvas, web storage, semantic elements, APIs — the standard today

Today we use HTML5. It is now maintained as a "living standard" — meaning it is continuously updated rather than released as numbered versions. It is governed by the W3C and the WHATWG. When you write HTML today, you are writing HTML5.

1.2 How Browsers Use HTML

When you visit a website, your browser performs a precise sequence of steps:

Browser Rendering Pipeline
1. Fetch — Browser requests the HTML file from the server via HTTP
2. Parse — Browser reads the HTML bytes and builds the DOM tree
3. Style — CSS is applied to DOM nodes (CSSOM built)
4. Layout — Browser calculates the position and size of every element
5. Paint — Pixels are drawn to the screen
6. Composite — Layers are combined into the final visible page

As a pentester, you need to understand step 2 (Parse) deeply. The parsing rules define what is valid, what is corrected silently, and what the browser ultimately treats as instructions — even if it looks broken on the surface.

💡
Browsers are forgiving parsers

Unlike most programming languages that crash on errors, HTML parsers are designed to recover gracefully from mistakes. A missing closing tag, an unclosed quote, or malformed attributes — the browser tries its best to render something useful. This tolerance has significant security implications you'll understand later in your studies.

1.3 HTML is Not a Programming Language

This distinction matters. HTML describes content and structure. It does not have loops, variables, or logic. That role belongs to JavaScript. Browsers read HTML top to bottom and build a visual representation. They do not "run" HTML — they render it.

Think of HTML as the skeleton of a web page, CSS as the skin and clothing, and JavaScript as the muscles and nervous system.

Chapter 02

How the Web Works

HTML doesn't exist in isolation. It is delivered over a network using the HTTP protocol. Understanding this delivery mechanism is as important as understanding the HTML itself.

2.1 The HTTP Request-Response Cycle

Every time your browser loads a web page, it performs an HTTP transaction: a request goes out, a response comes back. The HTML you study in this book is what arrives in that response body.

HTTP Transaction
  [ Browser ]                              [ Web Server ]
      |                                          |
      |  GET /index.html HTTP/1.1                |
      |  Host: example.com                       |
      |  User-Agent: Mozilla/5.0 ...             |
      | ────────────────────────────────────────>|
      |                                          |
      |  HTTP/1.1 200 OK                         |
      |  Content-Type: text/html; charset=UTF-8  |
      |  Content-Length: 1234                    |
      |                                          |
      |  <!DOCTYPE html>                         |
      |  <html>...</html>                        |
      |<─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─|

HTTP Methods

HTTP defines several methods (sometimes called "verbs") for different types of requests. As a pentester, you'll work with all of them:

Method Meaning Typical Use in HTML
GET Retrieve a resource Loading a page; clicking a link; <form method="get">
POST Send data to server Submitting a form; login; file upload
PUT Replace a resource REST APIs (not native HTML forms)
DELETE Delete a resource REST APIs (not native HTML forms)
HEAD GET without body Checking if a resource exists / its headers
OPTIONS Describe allowed methods CORS preflight requests
PATCH Partially update a resource REST APIs
📌
HTML forms only support GET and POST

Native HTML <form> elements can only use GET or POST. Other HTTP methods (PUT, DELETE, PATCH) are sent by JavaScript (the fetch() API or XMLHttpRequest), not by HTML forms directly.

HTTP Status Codes

Range Category Common Examples
1xx Informational 100 Continue
2xx Success 200 OK, 201 Created, 204 No Content
3xx Redirection 301 Moved Permanently, 302 Found, 304 Not Modified
4xx Client Error 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xx Server Error 500 Internal Server Error, 502 Bad Gateway, 503 Unavailable

2.2 URLs — The Address of Everything

A URL (Uniform Resource Locator) is the complete address of a resource on the web. Every link in HTML is a URL. Understanding every component of a URL is essential for a pentester.

URL Anatomy
  https://user:pass@shop.example.com:8443/products/shoes?size=42&color=red#reviews

  https     → Protocol (scheme) — how to connect
  user:pass → Credentials (rarely used — insecure)
  shop.example.com → Host (domain or IP address)
  8443     → Port (default: 80 for http, 443 for https)
  /products/shoes → Path (resource location on server)
  size=42&color=red → Query string (key=value pairs, after ?)
  reviews  → Fragment (anchor, after # — never sent to server)
🧠
The fragment (#) is never sent to the server

Everything after the # in a URL is handled entirely by the browser. The server never sees it. This is a crucial fact that you'll revisit when you study DOM-based vulnerabilities later in your security career.

Absolute vs Relative URLs

<!-- Absolute URL — complete address -->
<a href="https://example.com/about">About</a>

<!-- Relative URL — relative to current page's domain -->
<a href="/about">About</a>           <!-- starts from domain root -->
<a href="about.html">About</a>    <!-- relative to current path -->
<a href="../contact">Contact</a>  <!-- one directory up -->

<!-- Protocol-relative URL — uses the page's current protocol -->
<a href="//example.com/about">About</a>
Chapter 03

Document Structure

Every valid HTML page follows the same skeleton. Understanding this structure lets you instantly orient yourself when reading any web page's source code.

3.1 The Minimal HTML Document

<!DOCTYPE html>              <!-- Declaration: tells browser this is HTML5 -->
<html lang="en">             <!-- Root element; lang declares the language -->

  <head>                       <!-- Metadata section — NOT displayed on page -->
    <meta charset="UTF-8"/>   <!-- Encoding — declare within the first 1024 bytes -->
    <meta name="viewport" content="width=device-width, initial-scale=1.0"/>
    <title>My Page Title</title>  <!-- Browser tab title -->
  </head>

  <body>                       <!-- Visible content goes here -->
    <h1>Hello, World!</h1>
    <p>This is a paragraph.</p>
  </body>

</html>

3.2 The <head> Element in Detail

The <head> section contains metadata — information about the page, not the page's visible content. It is one of the richest sources of information when you're reading a site's source code. 

<head>
  <!-- Character encoding — defines how text is decoded -->
  <meta charset="UTF-8"/>

  <!-- Page description (shown in search results) -->
  <meta name="description" content="Online shop for shoes"/>

  <!-- Technology fingerprint — reveals the CMS or framework -->
  <meta name="generator" content="WordPress 6.4.1"/>

  <!-- Page title -->
  <title>Shop | Home</title>

  <!-- External stylesheet -->
  <link rel="stylesheet" href="/css/style.css"/>

  <!-- Favicon (browser tab icon) -->
  <link rel="icon" href="/favicon.ico"/>

  <!-- JavaScript file — defer means it runs after HTML is parsed -->
  <script src="/js/app.js" defer></script>

  <!-- HTTP-equivalent meta — can trigger a redirect -->
  <meta http-equiv="refresh" content="5; url=/new-page"/>
</head>
🛠️
Exercise 3.1

Open any website, press Ctrl+U (View Source). Find the <head> section. What can you learn about the site from it? Look for: framework/CMS hints, third-party scripts loaded, charset, description, and any unusual meta tags.

3.3 The <body> Element

Everything inside <body> is what the user sees and interacts with. The body can carry a handful of useful attributes: 

<body
  id="page-body"
  class="logged-in admin-user"   <!-- CSS classes — may reveal user role -->
  data-user-id="1042"            <!-- Custom data attribute — may leak info -->
>
💡
Class names on the body tag

Many web frameworks and CMS platforms (WordPress, Drupal, Django) add CSS classes to the <body> tag that include user role, page type, or feature flags. Reading these gives immediate context about the page and the user's permission level. You'll remember this during your first real reconnaissance session.

Chapter 04

Elements & Tags

HTML is made of elements. Each element is defined by tags. Understanding every major element — its purpose, its attributes, and its behaviour — is the core HTML skill.

4.1 Anatomy of an HTML Element

Element Anatomy
  <a  href="https://example.com"  target="_blank"> Click Here </a>

  a          → Tag name (defines what this element is)
  href       → Attribute name
  "https://example.com" → Attribute value
  <a ...>    → Opening tag
  Click Here → Content (text or nested elements)
  </a>       → Closing tag

Void Elements (Self-Closing)

Some elements have no content and no closing tag. They are called void elements. (In HTML5 the trailing slash is optional — <br> and <br/> are equivalent.) 

<br/>              <!-- line break -->
<hr/>              <!-- horizontal rule -->
<img src="x.jpg"/>  <!-- image -->
<input type="text"/> <!-- form input -->
<meta charset="UTF-8"/>
<link rel="stylesheet" href="style.css"/>

4.2 Block vs Inline Elements

HTML elements are traditionally classified as either block-level or inline-level. This determines how they flow on the page. (CSS can override the default with the display property.)

Block-Level Inline
Takes full width available, starts on a new line Only as wide as content, flows within text
<div>, <p>, <h1>–<h6>, <ul>, <li>, <table>, <form>, <header>, <section> <span>, <a>, <strong>, <em>, <img>, <input>, <label>, <code>

4.3 Heading Elements

<h1>Main Page Title — usually one per page</h1>
<h2>Major Section Heading</h2>
<h3>Subsection Heading</h3>
<h4>Sub-subsection</h4>
<h5>Less common</h5>
<h6>Least important heading</h6>

4.4 Text Formatting Elements

<p>A paragraph of text.</p>
<strong>Bold / important text</strong>
<em>Italicised / emphasized text</em>
<u>Underlined text</u>
<s>Strikethrough text</s>
<code>Inline code snippet</code>
<pre>Preserves whitespace and line breaks
  exactly as written</pre>
<blockquote>A quoted block of text</blockquote>
<span>Generic inline container — used for styling</span>
<div>Generic block container — the most used element</div>

4.5 List Elements

<!-- Unordered list (bullets) -->
<ul>
  <li>First item</li>
  <li>Second item</li>
</ul>

<!-- Ordered list (numbers) -->
<ol type="1" start="1">
  <li>First</li>
  <li>Second</li>
</ol>

<!-- Definition list -->
<dl>
  <dt>HTML</dt>
  <dd>HyperText Markup Language</dd>
</dl>

4.6 Semantic Elements (HTML5)

Semantic elements give meaning to the structure of a page. They tell the browser (and anyone reading the source) what role each section plays. You'll encounter these frequently when reading real application source code. 

<header>  Top of page — logo, nav  </header>
<nav>     Navigation menu  </nav>
<main>    Main unique content  </main>
<section> Thematic grouping  </section>
<article> Self-contained content (blog post, comment)  </article>
<aside>   Sidebar / tangential content  </aside>
<footer>  Bottom of page — links, copyright  </footer>
<figure>  Image with caption  </figure>
<figcaption> Caption for a figure </figcaption>
<time>    Date or time value  </time>
<mark>    Highlighted text  </mark>
Chapter 05

Attributes

Attributes provide additional information about HTML elements. They appear inside the opening tag and are written as name="value" pairs. Attributes are where much of HTML's power — and its attack surface — lives.

5.1 Attribute Syntax Rules

<!-- Standard: attribute="value" -->
<img src="photo.jpg" alt="A photo"/>

<!-- Single quotes are valid too -->
<img src='photo.jpg' alt='A photo'/>

<!-- No quotes (when value has no spaces) — valid but discouraged -->
<img src=photo.jpg/>

<!-- Boolean attribute — presence alone means true -->
<input type="text" required disabled readonly/>

<!-- Attribute names are case-insensitive (by spec) -->
<img SRC="x.jpg"/>   <!-- valid -->
<IMG SRC="x.jpg"/>   <!-- also valid -->

5.2 Global Attributes

These attributes can be used on any HTML element:

Attribute Purpose Example
id Unique identifier within the page. Must be unique. <div id="login-form">
class CSS class name(s) for styling. Multiple allowed. <p class="intro highlight">
style Inline CSS styles directly on the element. <p style="color:red">
title Tooltip text on hover. <abbr title="HyperText">HTML</abbr>
lang Language of the element's content. <p lang="ar">مرحبا</p>
hidden Hides the element from display. <div hidden>secret</div>
tabindex Controls keyboard tab order. <a tabindex="1">
contenteditable Makes the element's content editable by the user. <div contenteditable="true">
data-* Custom data attributes — store any data. <div data-user-id="42">

5.3 Event Attributes

Event attributes connect HTML elements to JavaScript code that runs when something happens. They follow the pattern on + eventname. Understanding these is fundamental — they are how interactivity is wired into HTML. 

<!-- Mouse events -->
<button onclick="handleClick()">Click Me</button>
<div onmouseover="showTooltip()" onmouseout="hideTooltip()">Hover</div>
<div ondblclick="editItem()">Double-click to edit</div>

<!-- Keyboard events -->
<input onkeyup="search(this.value)"/>
<input onkeydown="handleKey(event)"/>

<!-- Page/window events -->
<body onload="init()">                  <!-- runs when page finishes loading -->

<!-- Form events -->
<form onsubmit="validateForm(event)">   <!-- runs when form is submitted -->
<input onchange="recalculate()"/>      <!-- runs when value changes -->
<input onfocus="showHelp()"/>          <!-- runs when element gains focus -->
<input onblur="validateField()"/>      <!-- runs when element loses focus -->

<!-- Media events -->
<img src="photo.jpg" onload="imageLoaded()" onerror="showPlaceholder()"/>
<video onplay="trackPlay()" onended="showNext()"></video>
🧠
Why event attributes matter to pentesters

Event attributes are the bridge between HTML and JavaScript execution. Every element has dozens of potential event attributes. When you study web security later, you'll understand that these event hooks are how certain attacks work — injecting HTML that fires JavaScript through these event channels. For now, just learn what each event means and when it triggers.

5.4 data-* (Custom Data Attributes)

HTML5 introduced a way to store any custom data in an element using data-* attributes. These are extremely common in modern web applications and often reveal information about the application's internal workings. 

<!-- Developer stores application data in HTML -->
<div
  id="user-panel"
  data-user-id="1042"
  data-user-role="admin"
  data-api-endpoint="https://api.internal.com/v2"
  data-session-token="eyJhbGciOiJIUzI1NiIsInR5..."
>
</div>

<!-- JavaScript reads it via the dataset property: -->
<script>
  const div = document.getElementById('user-panel');
  const userId = div.dataset.userId;        // "1042"  (data-user-id)
  const role   = div.dataset.userRole;      // "admin" (data-user-role)
</script>
💡
Hyphens become camelCase

In the dataset API, a hyphenated attribute like data-user-id is read as dataset.userId. Developers sometimes place sensitive values (tokens, roles, internal endpoints) in these attributes — all of which are plainly visible in the page source.

Chapter 06

Links & Navigation

The anchor element <a> is what makes the web a web — it creates hyperlinks. Understanding every aspect of how links work is foundational for pentesting.

6.1 The Anchor Element

<!-- Basic link -->
<a href="https://example.com">Visit Example</a>

<!-- Open in new tab (rel=noopener stops the new page controlling this one) -->
<a href="https://example.com" target="_blank" rel="noopener noreferrer">New Tab</a>

<!-- Download link -->
<a href="/report.pdf" download="my-report.pdf">Download Report</a>

<!-- Anchor link — jump to element with id="section2" -->
<a href="#section2">Jump to Section 2</a>

<!-- Email link -->
<a href="mailto:admin@example.com">Email Us</a>

<!-- Phone link -->
<a href="tel:+20123456789">Call Us</a>
💡
Why rel="noopener" on target="_blank"

When a link opens a new tab, the new page historically received a window.opener reference back to your page and could redirect it somewhere malicious (a trick called reverse tabnabbing). Modern browsers now apply noopener automatically for target="_blank", but setting rel="noopener noreferrer" explicitly is still best practice — and noticing its absence on links to untrusted sites is something you'll do as a tester.

6.2 The target Attribute Values

Value Meaning
_self Default. Opens in the same tab/window.
_blank Opens in a new tab or window.
_parent Opens in the parent frame (if inside an iframe).
_top Opens in the full browser window, breaking out of any frames.
frameName Opens in a specific named frame/iframe on the page.

6.3 The <base> Element

The <base> tag, placed in <head>, sets the base URL for all relative links on the page. Every relative URL is resolved from this base instead of the page's actual URL. 

<head>
  <base href="https://cdn.example.com/" target="_blank"/>
</head>
<body>
  <!-- This will actually load: https://cdn.example.com/image.jpg -->
  <img src="image.jpg"/>
  <!-- This will go to: https://cdn.example.com/page -->
  <a href="page">Page</a>
</body>

6.4 The <nav> Element and Navigation Patterns

<nav aria-label="Main Navigation">
  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/about">About</a></li>
    <li><a href="/products">Products</a></li>
    <li><a href="/admin" class="admin-only">Admin</a></li>
  </ul>
</nav>
Chapter 07

Images & Media

HTML has rich support for embedding images, audio, and video. These elements load resources from URLs — making them important to understand for both functionality and resource analysis.

7.1 The <img> Element

<img
  src="https://cdn.example.com/photo.jpg"   <!-- image URL -->
  alt="A descriptive text"                   <!-- shown if image fails / accessibility -->
  width="800"                                 <!-- width in pixels -->
  height="600"                                <!-- height in pixels -->
  loading="lazy"                              <!-- defer loading until near viewport -->
  onerror="this.src='/placeholder.jpg'"       <!-- fallback on load error -->
/>

Image Sources

<!-- External URL -->
<img src="https://other-site.com/image.jpg"/>

<!-- Local path -->
<img src="/images/logo.png"/>

<!-- Data URL (image embedded directly as Base64 text) -->
<img src="data:image/png;base64,iVBORw0KGgo..."/>

<!-- SVG file (an SVG is XML and can contain <script>!) -->
<img src="/icons/logo.svg"/>

7.2 Audio and Video

<!-- Audio element -->
<audio controls loop>
  <source src="sound.mp3" type="audio/mpeg"/>
  <source src="sound.ogg" type="audio/ogg"/>
  Your browser does not support audio.  <!-- fallback text -->
</audio>

<!-- Video element -->
<video
  src="clip.mp4"
  controls
  width="640"
  height="360"
  poster="thumbnail.jpg"   <!-- shown before video plays -->
  muted                     <!-- muted (browsers require this for autoplay) -->
>
</video>

7.3 The <iframe> Element

An iframe embeds another HTML page inside the current page. It creates an isolated browsing context. This is one of the most important elements for a pentester to understand. 

<!-- Embed another page inside this one -->
<iframe
  src="https://maps.google.com/embed?..."
  width="600"
  height="450"
  title="Google Map"
  sandbox="allow-scripts allow-same-origin"  <!-- security restrictions -->
  loading="lazy"
></iframe>

<!-- Embed HTML content directly -->
<iframe srcdoc="<p>Inline HTML content</p>"></iframe>
💡
The sandbox attribute

The sandbox attribute restricts what an iframe is allowed to do. Without it, an embedded page can do anything a normal page can. With sandbox, capabilities are switched off unless explicitly re-granted using tokens like allow-scripts, allow-forms, allow-popups, and allow-same-origin. Note one important catch: granting both allow-scripts and allow-same-origin together lets the framed page reach back and remove its own sandbox — so that combination largely defeats the protection for untrusted content.

Chapter 08

Tables

HTML tables display structured, tabular data in rows and columns. They appear throughout web applications — in admin panels, data exports, reports, and API responses.

8.1 Complete Table Structure

<table>

  <!-- Caption (title for the table) -->
  <caption>User Accounts</caption>

  <!-- Table Head -->
  <thead>
    <tr>                              <!-- Table Row -->
      <th scope="col">ID</th>         <!-- Table Header cell -->
      <th scope="col">Username</th>
      <th scope="col">Email</th>
      <th scope="col">Role</th>
    </tr>
  </thead>

  <!-- Table Body -->
  <tbody>
    <tr>
      <td>1</td>                      <!-- Table Data cell -->
      <td>alice</td>
      <td>alice@example.com</td>
      <td>admin</td>
    </tr>
    <tr>
      <td>2</td>
      <td>bob</td>
      <td>bob@example.com</td>
      <td>user</td>
    </tr>
  </tbody>

  <!-- Table Footer -->
  <tfoot>
    <tr>
      <td colspan="4">Total: 2 users</td>   <!-- spans 4 columns -->
    </tr>
  </tfoot>

</table>

colspan and rowspan

<td colspan="3">Spans 3 columns</td>
<td rowspan="2">Spans 2 rows</td>
Chapter 09

Forms & Inputs — The Most Important Chapter

HTML forms are how users send data to servers. They are the primary interaction mechanism of web applications — and the primary target of web penetration testing. Master this chapter completely.

9.1 The Form Element

<form
  action="/api/login"         <!-- WHERE to send the data (URL) -->
  method="POST"               <!-- HOW to send it: GET or POST -->
  enctype="application/x-www-form-urlencoded"  <!-- body encoding -->
  name="loginForm"
  id="login-form"
  autocomplete="off"          <!-- hint to disable browser autofill -->
>
  ...form fields...
</form>

GET vs POST — Understanding the Difference

Aspect GET POST
Data location Appended to URL as query string: /search?q=term In the request body — not in the URL
Visibility Visible in the address bar, server logs, and browser history Not in URL — but not encrypted unless HTTPS is used
Bookmarkable Yes No
Size limit URL length limit (~2,000+ chars; browser/server dependent) No practical limit
Appropriate for Read operations — searching, filtering Write operations — login, register, submit
Idempotent? Yes (repeating the same request = same result) No (submitting an order twice = two orders)

The Three enctype Values

enctype Value Body Format When to Use
application/x-www-form-urlencoded username=alice&password=secret Default for all text-based forms
multipart/form-data Multipart MIME with boundaries Required when uploading files
text/plain Raw text, newline-separated pairs Rarely used in practice

9.2 Input Types — Complete Reference

The <input> element is polymorphic — its behaviour is entirely determined by its type attribute. Each type renders differently and sends data differently. 

<!-- TEXT INPUTS -------------------------------->
<input type="text"     name="username" placeholder="Enter username"/>
<input type="password" name="password"/>  <!-- masked characters -->
<input type="email"    name="email"   />  <!-- validates email format -->
<input type="tel"      name="phone"   />  <!-- phone keyboard on mobile -->
<input type="url"      name="website" />  <!-- validates URL format -->
<input type="search"   name="q"       />  <!-- search-styled text box -->
<textarea name="message" rows="5"></textarea>  <!-- multi-line text -->

<!-- NUMBER & RANGE ------------------------------>
<input type="number"  name="qty"   min="1" max="100" step="1"/>
<input type="range"   name="score" min="0" max="10"/>

<!-- DATE & TIME --------------------------------->
<input type="date"           name="dob"/>       <!-- YYYY-MM-DD -->
<input type="time"           name="appt"/>      <!-- HH:MM -->
<input type="datetime-local" name="meeting"/>   <!-- combined -->
<input type="month"          name="billing"/>

<!-- SELECTION ----------------------------------->
<input type="checkbox" name="agree" value="yes"/>  <!-- multi-select -->
<input type="radio"    name="plan"  value="basic"/> <!-- single-select per group -->
<input type="radio"    name="plan"  value="pro"/>

<!-- FILE & COLOUR ------------------------------->
<input type="file"   name="upload" accept=".jpg,.png" multiple/>

9.4 HTML5 Form Validation Attributes

HTML5 provides built-in client-side validation. The browser enforces these rules before submitting the form — unless JavaScript or proxy tools bypass the browser entirely. 

<input

/>

<input type="number" min="1" max="1000" step="1"/>
🔑
Client-side validation is a UX feature, not a security control

This is one of the most important things to understand before you start web pentesting. required, maxlength, min, max, and pattern all exist only in the browser. Any value sent via Burp Suite, curl, or a custom script completely bypasses them. The server must always validate all input independently. A server that trusts client-side validation is fundamentally broken.

9.5 Hidden Input Fields

Hidden inputs are part of the form but completely invisible to the user. They are submitted along with the form data and are commonly used to pass values the server set earlier (IDs, tokens, state).

  <input type="hidden" name="price"       value="129.99"/>
  <input type="hidden" name="user_role"   value="customer"/>
  <input type="hidden" name="csrf_token"  value="f83hd92k..."/>

  <button type="submit">Confirm Order</button>
</form>
🧠
Hidden ≠ Secret

A hidden input field is hidden only from the visual display. Anyone who looks at the page source, opens DevTools, or intercepts the request with a proxy tool can see every hidden field and change its value. The word "hidden" is purely a presentation term. Never confuse it with secrecy or protection.

Chapter 10

The Document Object Model (DOM)

The DOM is the browser's internal, living representation of the HTML page. It's a tree of objects that JavaScript can read and modify in real time. Understanding the DOM is essential for understanding how dynamic web applications behave.

10.1 HTML → DOM Tree

When a browser parses HTML, it builds a tree of nodes. Each HTML element becomes a node; attributes become properties of nodes; text content becomes text nodes.

DOM Tree for a Simple Page
  Document
  └── html
      ├── head
      │   ├── title
      │   │   └── #text "My Page"
      │   └── meta (charset="UTF-8")
      └── body
          ├── h1
          │   └── #text "Welcome"
          ├── p  (id="intro")
          │   └── #text "Hello World"
          └── form (action="/login" method="POST")
              ├── input (type="hidden" name="csrf")
              ├── input (type="text" name="username")
              └── button (type="submit")
                  └── #text "Login"

10.2 DOM vs HTML Source

The DOM is not the same as the raw HTML source. Browsers modify the DOM in several important ways:

  • Missing tags (<html>, <head>, <body>) are added automatically
  • Invalid nesting is silently corrected
  • JavaScript can add, remove, or modify nodes at any time
  • The DOM reflects the current state of the page — after all scripts have run
🛠️
Exercise 10.1 — View Source vs DOM

Open any modern website. Press Ctrl+U to view the original HTML source. Then press F12, go to the Elements tab, and look at the DOM. Notice the differences. In particular, look for content that exists in the DOM but not in the source — this is content added by JavaScript after page load. This difference is critical for understanding how dynamic web apps work.

10.3 DOM Node Types

Node Type Example Description
Element Node <div>, <p>, <a> HTML elements — most common
Text Node "Hello World" Text content inside elements
Attribute id="header" A property of an element node
Comment Node <!-- comment --> HTML comments — visible in the DOM!
Document Node document Root of the entire DOM

10.4 JavaScript and the DOM

JavaScript interacts with the DOM through the global document object. This is how web pages become dynamic: 

// Selecting elements
document.getElementById('header')         // by id
document.getElementsByClassName('nav-item') // by class (live HTMLCollection)
document.getElementsByTagName('input')     // by tag (live HTMLCollection)
document.querySelector('#login form')      // CSS selector — first match
document.querySelectorAll('input[required]') // CSS selector — all matches (NodeList)

// Reading content
element.textContent    // text only (safe)
element.innerHTML      // HTML markup as a string
element.value          // value of input/textarea/select
element.getAttribute('href')  // attribute value

// Modifying content
element.textContent = 'New text';
element.innerHTML   = '<b>Bold text</b>';
element.setAttribute('class', 'active');
element.style.color = 'red';

// Page-level information
window.location.href     // full URL
window.location.hostname // domain only
window.location.search   // query string (?key=value)
window.location.hash     // fragment (#section)
document.cookie           // non-HttpOnly cookies
document.referrer         // previous page URL
🧠
textContent vs innerHTML

textContent treats whatever you give it as plain text. innerHTML parses the string as HTML and builds real elements from it. That difference is the seed of an entire class of vulnerabilities you'll study later — for now, just remember that writing untrusted data with innerHTML is risky, while textContent is safe.

Chapter 12

HTML & JavaScript — How Pages Come Alive

JavaScript is the programming language of the web. It runs in the browser and interacts directly with the DOM. Understanding how HTML and JavaScript work together is foundational for web pentesting.

12.1 Including JavaScript

<!-- Inline JavaScript -------------------------------->
<script>
  console.log('Hello from inline JS');
  const name = 'Alice';
</script>

<!-- External JavaScript file ------------------------->
<script src="/js/app.js"></script>

<!-- async: downloads in parallel; runs as soon as it is ready (can interrupt parsing) -->
<script src="/js/tracker.js" async></script>

<!-- defer: downloads in parallel; runs after the HTML is fully parsed -->
<script src="/js/app.js" defer></script>

<!-- type="module": an ES module (deferred by default) -->
<script type="module" src="/js/main.mjs"></script>

12.2 JavaScript Reading User Input

A critical pattern to understand: JavaScript often reads data from the URL or from form inputs, processes it, and writes it back to the page. Understanding this flow is the foundation for understanding how data moves through a web application. 

<!DOCTYPE html>
<html>
<body>

  <h2>Welcome</h2>
  <p id="greeting"></p>

  <script>
    // 1. READ: get ?name= from the URL
    const params = new URLSearchParams(window.location.search);
    const name = params.get('name');   // e.g. URL: /page?name=Alice

    // 2. PROCESS: build a greeting string
    const message = 'Hello, ' + name + '!';

    // 3. WRITE: put it into the DOM
    document.getElementById('greeting').textContent = message;
    // textContent = safe (plain text only)
    // innerHTML   = UNSAFE if name comes from user input
  </script>

</body>
</html>

12.3 Cookies and JavaScript

Cookies are small pieces of data stored by the browser and automatically sent with every HTTP request to the matching domain. They are fundamental to how web sessions work. 

// Reading cookies from JavaScript
document.cookie;
// Returns: "session=abc123; theme=dark; username=alice"

// Setting a cookie from JavaScript
document.cookie = "username=bob; path=/; expires=Fri, 31 Dec 2027 23:59:59 GMT";

// Cookies with the HttpOnly flag CANNOT be read by JavaScript at all.
// They still exist and are still sent with requests, but document.cookie
// will not show them.
Cookie Attribute Purpose Security Impact
HttpOnly Cookie not accessible via JavaScript Protects the session cookie from JS access
Secure Cookie only sent over HTTPS Prevents interception over plain HTTP
SameSite=Strict Never sent with cross-site requests Strong CSRF protection
SameSite=Lax Sent only with top-level navigation Moderate CSRF protection (modern default)
SameSite=None Always sent cross-site (requires Secure) Enables cross-site use cases
Expires / Max-Age Sets when the cookie expires Persistent vs session cookie
Path URL paths the cookie applies to Scope limitation
Domain Domains the cookie applies to Scope — including subdomains

12.4 Web Storage APIs

HTML5 introduced two storage mechanisms that JavaScript can use to store data in the browser: 

// localStorage — persists until explicitly cleared
localStorage.setItem('authToken', 'eyJhbGc...');
localStorage.getItem('authToken');
localStorage.removeItem('authToken');
localStorage.clear();  // clears everything

// sessionStorage — clears when the tab/window is closed
sessionStorage.setItem('step', '2');
sessionStorage.getItem('step');

// Both are readable by any JavaScript on the same origin.
// Unlike cookies, they CANNOT be marked HttpOnly — always JS-readable.

14.2 What to Look for in Page Source

15.2 The Elements Panel

  console.log(e.name, e.value));

Chapter 16

HTML & HTTP Headers

HTML and HTTP headers are tightly connected. The headers the server sends control how the browser treats the HTML it receives — and they are one of the first things a pentester checks.

16.1 How Headers Relate to HTML

# HTTP Response — headers arrive BEFORE the HTML body
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 5234
Content-Security-Policy: default-src 'self'
X-Frame-Options: SAMEORIGIN
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=31536000
Set-Cookie: session=xyz; HttpOnly; Secure; SameSite=Strict
Referrer-Policy: strict-origin-when-cross-origin

# Body (HTML) starts here, after one blank line
<!DOCTYPE html>
<html>...</html>

16.2 Content-Type and Charset

The Content-Type header tells the browser how to interpret the response body. For HTML pages, it should always be: 

Content-Type: text/html; charset=UTF-8

If charset is missing or wrong, the browser may try to guess the encoding — and a mismatch between what the browser assumes and what the server actually sent can change how the page is interpreted. Always note the declared charset.

16.3 The Set-Cookie Header

The server creates cookies through the Set-Cookie response header. The browser stores them and sends them back with every subsequent matching request via the Cookie request header. 

# Server sends:
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Strict; Expires=Fri, 31 Dec 2027 23:59:59 GMT

# Browser sends back on every matching request:
Cookie: sessionId=abc123

16.4 Key Security Headers to Know

Header What It Controls Why It Matters to Pentesters
Content-Security-Policy Which scripts, styles, and images the browser may load If missing or weak, broader attacks become possible
X-Frame-Options Whether the page can be embedded in an iframe If missing, the page may be clickjackable
X-Content-Type-Options: nosniff Browser must respect Content-Type, not sniff it Prevents MIME-type confusion attacks
Strict-Transport-Security Forces HTTPS for a specified duration If missing, may allow an HTTP downgrade
Referrer-Policy How much URL info is shared with linked sites Prevents URL leakage to third parties
Permissions-Policy Browser features allowed (camera, geolocation...) Limits browser API exposure
Access-Control-Allow-Origin Which cross-origin requests may read the response Misconfiguration enables cross-origin data theft

For any header that IS present, note its value. This is a core skill you will use in every real-world web pentest.
